## 推荐定位

**一句话：为 HarmonyOS 用户提供原生连接入口，让已有 Mihomo 分流配置在手机上易于使用、更新和排障。**

这是产品方向，后半句的完整配置迁移体验仍需实现与验收。当前可对外表述为：**面向 HarmonyOS 的开源 Mihomo 客户端，提供原生 VPN 连接和 URL、文件、剪贴板配置导入。**

优先用户是已有 Mihomo YAML、桌面客户端或路由器分流经验的 HarmonyOS 用户：希望保留区域/服务策略，不愿在手机上重建全部配置。第二类是由可信配置提供者协助设置的普通用户：日常只需看状态、连接与更新。第三类是愿意复现问题、提交脱敏日志的开源贡献者。以上是基于产品能力的用户假设，尚无访谈或留存数据验证。

## 场景与用户价值

| 场景 | 要交付的结果 | 基线与验收边界 |
|---|---|---|
| 将电脑上生成的 YAML 带到手机 | 延续熟悉的服务分流，少改配置 | 基线有普通导入；迁移须校验组引用、provider、规则顺序及手机 DNS/设备规则差异 |
| 更新订阅 | 更新节点后仍保留自己的策略，失败可回退 | 来源更新已存在；自动重应用 Merge、事务激活与回滚待完成 |
| 外出、息屏或切换网络 | 看清连接状态，恢复可控 | 原生 VPN/运行时已有实现；后台稳定性、真实转发与恢复须真机矩阵验证 |
| 某服务不可用 | 找到命中规则与连接出口，减少反复试节点 | 临时原生组选择已存在；离线 Zashboard 与安全 REST/WS 接入待验收 |
| 多节点环境 | 减少手动选点，并能解释/关闭自动行为 | Smart 是研究方向；组存在、模型加载、预测参与必须分别验证 |

## 差异化与交付顺序

1. **熟悉的策略，适合手机的运行参数。** 迁移服务组与规则意图，平台 TUN/Controller 由宿主约束；不无差别继承家庭 NAS、网关设备规则或桌面 DNS。完整 YAML 与 provider 优先，Merge 需明确语义；原平台脚本可先导出最终 YAML。任意 JS/Shell 不作为已支持格式。
2. **日常操作简洁，深入诊断有入口。** 原生宿主负责系统授权、启停、状态、订阅和恢复；Zashboard 负责高级策略与连接观察。离线资源、安全认证与页面生命周期验收后才替换临时代理组页。
3. **恢复与更新值得信任。** 明确区分系统隧道、内核就绪和真实健康；失败保留有效配置，用户主动停止优先。可复现构建、脱敏诊断及固定上游身份支持长期维护。
4. **可选择的智能选点。** Smart 需先证明实际连接经过策略与预测路径，模型许可明确，再谈减少手工切换；LightGBM 单独开关和失败行为要可见。

原生架构不是独占优势，ClashBox、ClashOH、Paws 和 TunBox 已有相关实现；内置 Zashboard 也已有 Clash Mi。可形成差异的是上述流程的整体验收。轻量、稳定、易用、功能完整是设计目标；包体/内存/耗电/恢复耗时没有同条件测量前，不宣传领先或保证。

项目交付客户端与配置工具；用户自行提供网络服务与配置。开源和可维护性由可重建来源、许可声明、必要回归和兼容边界支撑，不用功能数量代替质量。

## 待评审与协作契约

- 产品评审：是否优先服务配置迁移用户；日常原生入口与高级面板的职责划分是否接受。
- 配置线提供：格式支持清单、合成迁移样例、更新/失败回滚结果；兼容性线确认区域/服务策略语义与手机例外。
- Controller/面板线提供：认证、离线资源、退出不停止 VPN 的验收；任何未合入分支不自动成为宣传事实。
- Smart 线提供：固定内核/模型身份、许可、预测参与与关闭/降级行为；运行时线提供真机后台/网络切换矩阵。
- 发布线提供：可复现构建与资源清单。名称评审独立进行，用户定稿和冲突复核后再单独讨论更名。
